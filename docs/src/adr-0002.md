# ADR 0002: Extract the engine by moving contracts, not by wrapping rules

- Status: accepted
- Date: 2026-09-01

## Context

Three capability waves (`property-comparison`, `property-required`,
`property-predicate`) were migrated into Axioval using a per-family *sidecar*:
a `families/<name>/axioval.rs` adapter inside the legacy runtime that translates
the legacy rule into an Axioval `CompiledRule`, evaluates it, and translates
the findings back.

Measured outcome of that approach across the three waves:

| Metric | Value |
|---|---|
| Net LOC added to the legacy runtime (`rules` + `checker`) | `+9110` |
| Capabilities owned by `axioval-rules` | 7 |
| `impl Rule for` in the legacy runtime | 83 |
| Native rule LOC replaced | 0 (native paths retained beside sidecars) |

The sidecar keeps both implementations alive by construction: a supported
declaration goes to Axioval, everything else stays native. The legacy runtime grows on
every wave, and the engine never becomes the owner. Extrapolated, the remaining
76 rule implementations add roughly an order of `10^5` LOC to the vendor tree
before the engine is extractable.

### Root cause

The blocker is not rule policy. It is the shape of the evidence seam.

`crates/rules/src/evidence/core/source.rs` declares `GeometryProvider` with
**43 methods**, of which:

- **23** take a `spec::rule::*PlanSpec` — `resolve_stair(&StairPlanSpec)`,
  `resolve_parking(&ParkingPlanSpec)`, `resolve_escape_route(...)`, and so on;
- **12** take a neutral `EntityRef`.

A provider method named after a rule *is* rule policy. Each rule therefore owns
a bespoke evidence method, so migrating one rule means porting one provider
method plus its `PlanSpec` plus its adapter — the cost never amortizes. Axioval
already has the correct opposite shape: 7 narrow, capability-scoped, snapshot-
bound services (`PropertyResolutionService`, `FreeSpaceService`,
`MetricRoutingService`, `WalkabilityService`, `RelationshipSelectionService`).

### What is already neutral

`crates/spec` is 21,363 LOC with **zero internal dependencies** — it imports no
`model`, no `geometry`, no `codec`. It is the format-neutral statement of what a
rule *is*: definitions, parameters, units, enum domains, severities,
classification expressions. It is already the engine's contract layer, living in
the vendor tree.

## Decision

Extract the engine by moving the **contract and the runtime** first. Rule
families follow mechanically afterwards, instead of one bespoke sidecar at a
time.

### Target ownership

| Concern | Owner | Source today |
|---|---|---|
| Rule vocabulary, parameters, units, classification | `axioval-ir` | `crates/spec` |
| Compile, registry, selection, quantifiers | `axioval-engine` | `rules/src/engine`, `rules/src/engines` |
| Pairwise, circulation, free-space algorithms | `axioval-engine` | `rules/src/engines` |
| Rule policy per family | `axioval-rules` | `rules/src/families` |
| IFC semantic evidence | `axioval-ifc` | `rules/src/adapters/ifc` (semantic half) |
| Geometric evidence | `axioval-axiolid` | `rules/src/adapters/ifc` (geometric half) |
| CSET/SMC byte formats, authoring, CLI, Python | the legacy runtime | unchanged |

The legacy runtime keeps exactly one job: **vendor compatibility**. Reading and
writing its proprietary binary formats, and mapping them onto Axioval contracts. It
becomes one application among several, not the home of the engine.

### The seam rule

An evidence service may be parameterized by *geometry and identity*. It may
never be parameterized by a rule. Concretely:

```rust
// prohibited — rule policy inside the evidence contract
fn resolve_stair(&self, plan: &StairPlanSpec) -> QueryOutcome<StairFacts>;

// required — neutral capability, rule policy stays in axioval-rules
fn treads(&self, object: ObjectId) -> Evidence<TreadGeometry>;
```

The 23 `PlanSpec`-shaped methods are the migration backlog, and each one is
retired by decomposing it into neutral evidence plus policy in `axioval-rules`.

### Sidecars are frozen

No new `families/<name>/axioval.rs` sidecars. The three that exist are the
proof-of-seam and are removed when their families move to `axioval-rules`.
Their exactness semantics — all-row support, terminal inexactness, request
deduplication, source-qualified evidence — are preserved as engine-side
contracts, not vendor-side adapters.

## Consequences

- Legacy runtime LOC decreases monotonically after the `spec` move; today it increases.
- Rule families port as policy only, against evidence that already exists.
- A independent application becomes writable once `spec` and the runtime are in
  the engine, without waiting for all 83 rules.
- The migration ledger's per-rule rows stop being the unit of progress; the
  contract and runtime waves become the unit.
- Short term, the legacy runtime depends on a much larger Axioval surface, so the
  facade must publish the contract types before any family moves.

## Rejected alternatives

- **Continue per-family sidecars.** Measured to be anti-convergent above.
- **Fork the vendor tree into the engine wholesale.** Imports `model`,
  `geometry`, `codec` and the vendor's Java-compat semantics into a neutral
  repository, which ADR 0001 prohibits.
- **Publish `spec` as its own crate outside Axioval.** Creates a third
  vocabulary next to `axioval-ir` and its normalized package contract.
