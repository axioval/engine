# ADR 0005: Built-in capabilities are templates over composable parts

- Status: accepted
- Date: 2026-10-07
- Extends: ADR 0004 (decompose plan-shaped evidence into measurement and policy)

## Context

ADR 0004 split measurement from policy at the service boundary: a service
returns what it measured, a capability decides what it means. Inside the
rules crate, each capability still measured and decided in its own code.
About 35 capabilities held geometric knowledge no other rule could reach:
a slope measured for a ramp could not be reused for an embankment or a
cross fall, and a stricter variant of a check needed new Rust.

Composable rules ([#225](https://github.com/axioval/engine/issues/225))
gave authors the parts: measured values registered with typed descriptors,
a total expression language over intervals with three-valued truth,
selectors and generic judges. With those parts in place there were two
ways forward for the built-ins. Retire the capabilities and ship their
checks as expression rules, or keep them and rebuild them on the parts.

Retiring them would break every package, the catalogue's entries and the
export profiles, which address a capability as one rule type with its
parameters, as external rule formats know these checks. It would also
lose what an expression rule does not state: a capability's own wording,
graded findings, report tables and declaration checks.

## Decision

A built-in capability keeps its **outside contract** and is defined inside
as a **template**: a preconfigured composition of measured values,
expressions, selectors and a generic judge, held as data
(`axioval_engine::template::Template`) and run by the same evaluator as an
`expression` rule.

- The outside contract is the capability id, its parameter descriptor,
  how a declaration is refused, and every finding and not-evaluated
  outcome with its scope, wording, related objects, evidence exactness and
  grade. `crates/engine/rules/tests/golden/descriptors.json` pins the
  descriptor of every built-in; a rebuild never changes it.
- Measurement lives in measured values, decision in expressions and
  generic judges. Searches (routes, pairings, free-floor fits, sight
  lines, allocations) stay in Rust and state their answers as measured
  lists the template judges.
- Templates are engine-owned. A package never supplies one, and nothing in
  a template runs package code.
- The catalogue shows each template's composition as expressions and
  block trees (expand), and a rule bound to a template can be copied into
  the `expression` rule it composes (fork) as the start of a stricter or
  extended rule.
- A rebuild is done only when the [parity harness](./parity.md) holds the
  template to the replaced implementation on every fixture, on generated
  inputs and on the outcomes recorded on pinned public models, and the
  [benchmark](./performance.md) holds it within budget.

58 of the 70 built-in capabilities run as templates, among them every
generic judge and every capability the rebuild issues #280 to #287 listed.
The remaining twelve (`expression`, `quantity-takeoff`,
`model-comparison`, `manual-issue` and the simple property, profile,
classification and container checks) run as before; their descriptors
are pinned all the same.

## Consequences

- **Export as single rule types.** A rule bound to a template exports
  exactly as before the rebuild: as that capability with its parameters,
  or refused by a profile that has no form for it. A forked rule is an
  `expression` rule and exports only where a profile states every node
  (`ExportProfile::expression_kinds`), otherwise refused naming the first
  node it cannot state.
- **A parity reference is kept.** Each replaced implementation stays in
  `<capability>/reference.rs`, exported as `axioval_rules::reference::*`
  and compiled only with the rules crate's `parity-reference` feature,
  which its own tests turn on. It is no capability of any registry, and
  release binaries do not contain it: the architecture gate refuses an
  allowance of dead or unused code switched by that feature, and the lint
  section runs clippy on the libraries without it
  ([#295](https://github.com/axioval/engine/issues/295)). Every accepted
  difference between a template and its reference is recorded with its
  reason and decision (D1 to D40); most are fail-closed outcomes where a
  selection cannot be listed whole.
- **A performance budget.** A template reads values through the same parts
  an expression rule reads, which cost more per value than a capability
  calling its services. The budget is 1.25 times the replaced
  implementation's run time and 1.5 times its peak heap per input, judged
  with a 99% interval over repeated rounds
  ([#293](https://github.com/axioval/engine/issues/293)). The runner keeps
  close by binding plans once per rule, memoizing measurements per run,
  reading values in batches and sharing selections between rules. An input
  may exceed the budget only as a recorded exception with its own ceiling
  in `scripts/bench_budget.json`; on a public model only when judged with a
  stated confidence and tracked by an issue that removes it. Eight such
  known misses of 1.25 to 1.30 times remain, tracked in
  [#296](https://github.com/axioval/engine/issues/296).
- **One implementation per quantity and per comparison.** A measured value
  calls the capability's own function, never a copy, and every rule
  compares through `axioval_engine::comparison`. Where the rebuild found
  two implementations disagreeing, one became the contract, recorded as a
  divergence (a stated `-0` now equals `0` in `property-comparison`, D20).
- **Improvements are shared.** A better measurement or judge improves every
  template and every expression rule that reads it; a new capability is
  written as a template from the start
  ([Rebuilding a capability as a template](./templates.md#rebuilding-a-capability-as-a-template)).

## Enforcement

`crates/engine/rules/tests/descriptors.rs` fails on any change to a
built-in's descriptor. The parity tests, with the CI `parity` job on the
pinned public models, fail on any difference a case does not record and on
a recorded one no longer shown. `scripts/architecture.py` maps every
measuring call site in the rules crate to a registered measured value or a
reviewed search kind (`scripts/measurement_ledger.json`) and refuses a
tolerance defined twice. `scripts/bench.py gate` fails a template over its
ceiling.
