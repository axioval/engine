# ADR 0006: Compute once: a derivation store shared by a check's rules

- Status: proposed
- Date: 2026-10-19
- Extends: ADR 0005 (built-in capabilities are templates over composable parts)

## Context

Most rule sets ask the same few expensive questions many times: a space's
placement scene (its floor less its obstacles), a spatial index over a set
of bodies, the members of a relationship, a body's frame. Where the engine
already answers such a question once and reuses it, the gains are large.
Sharing the candidate universe of a relationship walk took a whole check
from 15 s to 0.12 s ([#429](https://github.com/axioval/engine/issues/429)).
Keeping a space's regions in its scene halved a second rectangle search
([#427](https://github.com/axioval/engine/issues/427)).

That reuse exists today in several separate places, each with its own
rules:

- **The run's `MeasuredMemo`** (`axioval_engine::measured`) keeps what
  measured-value providers and shared selections compute, keyed by type
  and by everything the value depends on. It lives for one run. It has no
  bound on its size and no notion of when an entry is last read, and two
  threads asking for one key at once both compute it.
- **Service-local caches** in the adapters: a few kept placement scenes per
  thread (`KEPT_SCENES` in the free-space service, a derivation since
  #408), indexes built once
  behind a `OnceLock` (levels, attributes, classifications, glazing,
  metric routing). They live as long as the session and are not counted
  against any budget.
- **Shared values** such as `CandidateUniverse`, passed by `Arc`.

So a circle rule and a rectangle rule over the same spaces still build each
space's scene separately unless they happen to share a thread's ring
([#408](https://github.com/axioval/engine/issues/408)). No cache knows the
check's memory budget ([#407](https://github.com/axioval/engine/issues/407)),
and nothing survives from one check of a model to the next check of its
revision ([#409](https://github.com/axioval/engine/issues/409)).

Reuse is also where an engine that fails closed can go wrong without any
test noticing:

1. **An incomplete key** hands one question's answer to another. Every input
   that can change a result has to be in the key: the objects and their
   revision, the tolerance, the frame, the parameters, the precision mode,
   and the engine's and kernel's versions.
2. **Memory.** A kept answer is memory held on purpose. The free-floor
   searches only just stopped exhausting their host
   ([#419](https://github.com/axioval/engine/issues/419),
   [#434](https://github.com/axioval/engine/issues/434)).
3. **Order dependence.** If rule B succeeds only because rule A happened to
   build something first, a report changes with rule order and thread count.
   Reports are byte-identical whatever the threads
   ([#405](https://github.com/axioval/engine/issues/405)).
4. **Precision classes.** The overlay's Fast morphology is promised only on
   its certified side and its stated excess, not bit for bit across
   releases. A Fast answer must never answer an Exact question.
5. **Concurrency.** Two threads asking for one key at once should build it
   once, not twice and not under a lock held while building.
6. **Observability.** When reuse decides the run time, "why is this slow"
   becomes "what was not reused", and a run has to be able to say.

## Decision

Expensive, reusable work is stated as **derivations** and answered through
one **derivation store** per check. Each derivation is a pure function of
its key, so whether a value was built or reused can never be seen in a
report.

- **A derivation** is a typed query with a key and a value:
  `scene(space, obstacles, tolerance, mode)`, `index(bodies, frame)`,
  `members(relationship)`, `frame(body)`. A derivation reads only its key
  and other derivations, never a rule. Derivations are engine-owned or
  adapter-owned, like templates. A package never supplies one.
- **A key is a fingerprint** of the source-qualified identities and
  revisions of its inputs, its parameters, its precision class, and a
  version that the crate defining the derivation bumps whenever its
  results can change (and that names the kernel crates it calls).
  A key is compared field by field, never by a formatted string. A test
  holds every derivation's key to change when any one input changes.
  See [Complete keys](#complete-keys) for how this is held.
- **The store** keeps values by key behind `Arc`. It builds each key at
  most once at a time: a second caller waits for the first and gets its
  value (single flight). It builds without holding the store's lock.
- **Lifetime is planned, not guessed.** The compiled plan knows every rule
  of the check before it runs, so it knows which derivations each rule
  reads. The store releases a value after its last reader, and evicts to
  stay within the check's memory budget when the plan cannot say. Eviction
  only ever costs time, never changes a result.
- **Cost is charged as if built.** A rule is charged a derivation's cost
  against its work budget whether the store built the value or reused it.
  A refusal therefore never depends on what was cached, and reports stay
  identical under any rule order, thread count, or with the store
  disabled. The free-floor work budget of #434 already charges kept
  regions this way.
- **Precision is part of the key.** An Exact question is answered only by
  an Exact value. A Fast value carries its excess, and only a question
  that accepts Fast reads it.
- **A run reports its reuse.** Each derivation kind's hits, misses, bytes
  held and build time are available in a run's statistics, and
  `axioval check --stats` prints them (see [The reuse report](#the-reuse-report)).
- **The store's API** ([#437](https://github.com/axioval/engine/issues/437)).
  `axioval_engine::derivation` holds it. A `DerivationKind` names a key
  type, a value type and `build(key, inputs)`, where `Inputs` reads other
  derivations and the check's services and nothing of a rule. A run
  installs one empty `DerivationStore` among its services, where the
  engine reaches it, and makes it the thread's current store
  (`derivation::current`) on every worker, where a geometry adapter, handed
  a request and never the registry, reaches it. No core crate depends on
  an adapter. `derive` answers an `Arc` of the
  value. A failure of the derivation's own is part of its value
  (`Result<T, E>`), kept and shared, since a pure build fails alike for
  every caller. Only a cycle is an error of the store
  (`DerivationError::Cycle`): a build that would wait on itself, on its
  own thread, through other threads' waits, or on a worker of the thread
  building it, is reported instead of waited on. A build that panics keeps
  nothing, and its waiters build the key themselves. Each kind counts its
  hits, builds, waits, build time, releases, evictions and the bytes its
  `size_hint` states (held now and at most), for the reuse report (#442)
  and for charging the memory budget (#407, #440). A precision class
  (#438) is a field of a kind's key; its version (#439) is the kind's
  `VERSION`, which keys every value of the kind beside its key.
- **`MeasuredMemo` becomes a view of the store, not the store.** Its shared
  table keeps each key and value type as a kind of the run's store, built
  by the closure a provider passes, so a measurement is taken at most once
  at a time. The memo stays the providers' interface: their closures read
  the rule context the run hands them, which a pure derivation never sees,
  and the per-rule table (`of_rule`, dropped by `end_rule`) has a lifetime
  of one rule, not of the check. Work that a rule's context does not
  shape moves onto typed derivations kind by kind (#443).

The store comes in three stages:

1. **Within a check.** Free-floor scenes, spatial indexes and relationship
   members move onto the store, and `MeasuredMemo` becomes a view of it.
   Circle and rectangle rules then build each space's scene once
   (#408).

   Placement scenes and indexed bodies are derivations now (#408): the
   free-space service's `PlacementScenes` (keyed by the service's state,
   scope, merged scopes, obstacles, swept doors, band, tolerance and
   precision) replaced `KEPT_SCENES`, and the proximity
   service's `IndexedBodies` (geometry, object, void and tolerance)
   indexes each body a clash, clearance or distance pair reads once per
   check. A geometry service's methods are handed a request, never the
   registry, so they reach the store as the thread's current one
   (`derivation::current`), entered by the runtime and on every worker as
   the memory budget is. Kept values are held against the memory budget,
   and each kind keeps at most a quarter of it, releasing the values read
   least recently; releasing after the last reader is the planner's
   (#440).
2. **Across a check's rules, at plan time.** The planner orders rules so
   that derivations are built once and released early, and only meshes the
   objects some derivation can read
   ([#410](https://github.com/axioval/engine/issues/410)).
3. **Across checks and revisions.** A content-addressed store on disk
   answers a derivation whose inputs did not change since the last check,
   so a revised model, or a rule added later, re-derives only what its
   changed inputs reach (#409). A stored value is trusted only when its
   key, versions and integrity hash all match, and is otherwise rebuilt.

### Complete keys

[#439](https://github.com/axioval/engine/issues/439) holds every kind's key
to all of its inputs, three ways:

- **A version per kind.** `DerivationKind::VERSION` is a
  `DerivationVersion`: a revision the defining crate bumps whenever the
  same key could build another value, and the kernel crates the build
  calls (`Kernel`: name and version). It is a constant of the kind rather
  than a field of every key, so no kind can leave it out: the store keys
  every value of a kind by it beside the key, which within one check is
  one version a kind, and the disk store of #409 writes it with every
  value. Each kind's test checks the kernels it names against the
  versions the workspace's `Cargo.lock` locks
  (`DerivationVersion::unlocked`), so a kernel upgrade fails until the
  kind names the new version, and its revision is bumped where results
  can change. `check --stats` prints each kind's version.
- **Field by field.** Keys derive or implement `Eq` and `Hash` over their
  fields, floats by their bits, a service's state by its identity. The
  architecture gate refuses a kind keyed by a formatted string
  (`type Key = String` and the like).
- **A key-completeness test per kind.** `KeyCompleteness::<Kind, _>`
  starts from a key of known inputs and changes each input in turn: the
  key has to change (`input`), and where the input affects the value, the
  value has to change too (`changes_value`), compared by a fingerprint the
  test chooses and built in a store of its own. Keys built from the same
  inputs must be equal and hash alike (`same`). The architecture gate
  (`scripts/architecture.py`, `derivation_kind_violations`) finds every
  `impl DerivationKind for <Kind>` in a crate's `src/` and refuses one that
  no `KeyCompleteness::<Kind` of the same crate names; it fails when it
  finds no kind at all, so it cannot go inert. Kinds in `tests/` are the
  store's own fixtures and are exempt.

`PlacementScenes` and `IndexedBodies` have such tests: every input
changes the key, and each one a small fixture can show changes the value
(a scene's scope, merged scopes, obstacles, swept doors and band; a body's
geometry, object, void and linear tolerance). The rest (the service's
identity over equal geometry, the obstacles' order, the tolerances the
overlay or audit does not read here) are held to change the key only.
A scene's precision has one class (Exact) until #438 adds Fast.

The memo's tables have no version: they are views of one run's store,
built by a provider's closure over the rule context, and keep nothing
past the run, so no value is ever read under another version. Their keys
are each provider's own types and are not under the gate; the work moving
onto typed kinds (#443) brings each one under it, test and version
included.

### The reuse report

[#442](https://github.com/axioval/engine/issues/442): each kind's
`DerivationStatistics` carries its version, hits (a read answered by a
held value, a waited-for one included), builds (the reads none answered),
waits, the time its builds took (summed over threads), the bytes held now
and at most, the values released by name, and those evicted to keep
within the kind's bound. Counts are taken under the store's lock; the
build time from a clock around each build. `Runtime::with_derivation_observer`
hands them to a host at the end of each run, and `axioval check --stats`
prints them on stderr, one tab-separated line a kind after a header
(see [the CLI](./cli.md#axioval-check)). They never reach a report, so a
report with `--stats` is the report without it, byte for byte.
`--timings` printed a line a kind before; it now leaves them to `--stats`
and keeps to phases.

## Consequences

- **A new rule is faster when it is made of known parts.** A capability or
  expression rule that reads derivations another rule already built pays
  only for its own judgement. This is the ADR 0005 parts model carried
  from evaluation into computation.
- **Adapter caches give up their own lifetimes.** `KEPT_SCENES` and the
  service `OnceLock`s become derivations, or stay only where the value is
  part of the source itself (a parsed schema, a model's index).
- **Determinism is tested directly.** A gate runs a rule set in its own
  order, reversed, on one and on several threads, and with the store
  disabled, and requires the reports to be byte-identical. It runs over a
  generated building in every gate and over the public parity models in
  CI ([#441](https://github.com/axioval/engine/issues/441); see
  [The determinism gate](./parity.md#the-determinism-gate)), where every
  budget is also held to charge a reused value as if built. A run-wide
  budget that refuses whichever rule comes next is the exception still
  open ([#447](https://github.com/axioval/engine/issues/447)).
- **Memory is bounded by the plan.** A check holds a derivation only while
  a rule still to run reads it, and within the budget of #407.
- **The disk store is a compatibility surface.** Its key format and
  versions are a contract. A stale or altered entry is rebuilt, never read.

## Not decided here

- The disk format and where it lives.
- How fine derivations should be. Each stage measures that: a derivation
  that costs more to key and keep than to build is not one.
