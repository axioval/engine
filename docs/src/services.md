# Typed host services

The engine passes a `RuleContext` containing the immutable project view and a type-indexed `ServiceRegistry` to trusted capabilities. Applications register semantic or computational services explicitly; duplicate concrete service types are rejected instead of silently replacing an implementation.

Adapter crates are peers:

- OpenBIM implementations can provide semantic/property/relationship services.
- Axiolid implementations can provide geometry services for IFC, proprietary CAD, or any source able to lower geometry into Axiolid.
- ICDD implementations can provide project assembly and cross-document link services.
- Alternate geometry backends register the same source-neutral service interfaces.

Services reach a run through its `EvidenceSession`, bound to the source snapshots they were built from. An adapter's service records its own snapshots (`with_service`). A service the host builds itself, such as geometry meshed from the same file, records only a source identity, so the host states the snapshots it was built from (`with_host_service`). Both are checked the same way: at least one binding, no source twice, and every binding equal to the session's snapshot, so a service built from another revision is refused.

A session may hold several sources. An adapter builds one session per source, and `EvidenceSession::federate` combines sessions over disjoint sources into one: the project holds every object under its own source-qualified identity, every snapshot and declared discipline is kept, and each semantic service the members registered (property resolution, relationship selection, type hierarchy, classifications, integrity, object frames, coordinate systems) becomes one service bound to the snapshots of the members that had it. Each request goes to the member that owns its source (a property's object, a relationship's anchor, a classified or framed object, an integrity scan's source); a source no member covers is refused, never answered empty. A relationship request is answered over the part of its candidate universe in the anchor's member, since a member cannot relate objects it does not hold, and the answer is bound back to the whole request. Two members holding one source are refused (`DuplicateSource`), and so is a member that already holds a service federation cannot route by source (`UnfederableService`): register host services such as geometry on the federated session, bound to every snapshot they were built from. One member is returned unchanged.

A snapshot need not contribute an object. A model holding no objects (an IFC file with only presentation data, say) is an empty source: `EvidenceSession::try_new` accepts it, alone or beside other sources, and federation keeps it as a member like any other. Only an object whose source has no snapshot (`MissingSource`) and two snapshots of one source (`DuplicateSource`) are refused. So that an empty source is judged rather than silently absent, the runtime installs the run's sources per run as `SessionSources`, replacing any host-registered copy: every snapshot's source in `Runtime::run_session`, the sources the objects name in `Runtime::run` over a bare project. A capability forming one scope per source (`object-count`, `table-allocation` without anchors) starts from these, so "the model contains a building" fails on an empty model instead of passing because nothing was counted.

A source's discipline (`EvidenceSession::with_discipline`) is a host declaration, not part of the snapshot identity: services bound to a snapshot stay valid whatever discipline the source plays. The runtime installs the session's declarations per run as `SourceDisciplines`, replacing any host-registered copy, as it does concept bindings.

Rule packages cannot register services and cannot supply executable code. Missing required services must produce an explicit not-evaluated/backend-unavailable outcome, never a pass.

Property resolution is exposed through `PropertyResolutionServiceHandle`. A present response is a `ResolvedProperty` bound to the complete `PropertyRequest`, including the source-qualified object identity and property key; absence requires equivalent exact request-bound evidence. The handle rejects cross-object substitution, mismatched property keys, absent provenance, approximate values, non-finite numerics, and non-reviewable absence claims. Built-in property capabilities and property-based selectors require this service rather than treating a missing entry in an object map as proof of absence.

Relationship-based comparison candidates are exposed through `RelationshipSelectionServiceHandle`. A request binds the checked object, the complete selector-derived candidate universe, and either a shared-group or directional traversal query. Successful responses must stay inside that universe, use canonical unique object IDs and evidence, and prove exact completeness. Source adapters interpret native containment, hosting, and relationship structures; the engine does not read `Object.relationships` as authoritative source semantics.

Relationships derived from geometry are exposed through `DerivedRelationshipServiceHandle`. It answers the same `RelationshipSelectionRequest`s for identities starting with `axioval:derived.`, returning a `CompleteRelationshipSelection` or a refusal. `EvidenceSession::with_derived_relationships` registers it and replaces the session's relationship handle with one that routes those identities to it and every other identity to the semantic service registered before, so every capability that takes a `relationship` or a `path` uses derived relationships unchanged. The identity names the derivation and fixes its tolerances as `;key=value` pairs; an unknown derivation, an unknown or repeated key, or a negative, non-finite or out-of-range value is an invalid request, never an empty answer. The handle refuses a selection whose evidence does not name its derivation.

| Identity | Edge | Parameters (default) |
|---|---|---|
| `axioval:derived.contained-in-space` | an element to every space whose body contains its reference point; when none does, to the single nearest space whose surface lies within `horizontal` metres in plan and `vertical` metres in elevation of it | `horizontal` (0), `vertical` (0) |
| `axioval:derived.adjacent-space` | a door, window or opening to the spaces a probe first enters on each side of it within `reach` metres; a side that enters none is outside | `reach` (1) |
| `axioval:derived.overlapping-group-space` | a space to every larger space covering at least `ratio` of its footprint whose vertical extent lies within `vertical` metres of its own | `ratio` (0.5), `vertical` (0) |

Edges run from a subject to a space: `forward` from a component reaches its space, `backward` from a space reaches its components or doors. Tolerances live in the identity rather than in a request field so that the request contract stays the one every relationship capability already builds, and two rules asking with different tolerances ask visibly different questions. An undecided case refuses the whole answer: an unmeasured or bodiless space, an unmeasured subject in the universe, a reference point or probe start on a space boundary, two equally near spaces, or tessellated geometry close enough to change the answer.

The adjacency evidence records sides, and that record is a contract: after the canonical identity and a colon, a provider cites `{subject}->{space}:side={+|-}…` for every space a probe first entered and `{subject}:side={+|-}…:outside…` for a face that entered none, `+` being along the element's through-thickness normal. `adjacent_side` reads a locator back as an `AdjacentSide` for a given subject and space (or outside), so a capability can require the spaces of an internal door on opposite faces.

Object frames are exposed through `ObjectFrameServiceHandle`: for an object, its placement frame as a `MetricFrame` (origin in canonical metres, right-handed orthonormal right, forward and up axes) grounded on that object, and an `ObjectFront`. The handle refuses objects of a source the service does not cover and a frame naming another object; the frame's evidence must be exact, reviewable and from the object's source. The frame's axes are the source's placement axes: `forward` is the placement's second axis and says nothing about which side of the object is its front. A front is `Stated` only where the source states one and `NotStated` otherwise, never inferred from the axes, the shape or the object's type. An object whose source states no placement is `NotPlaced`, never placed at the origin. Semantic adapters provide this service, so capabilities can use it without geometry. Door and window leaves (hinge side, swing sector) are not part of this contract yet.

Source coordinate systems are exposed through `CoordinateSystemServiceHandle`: for a source, a `SourceCoordinateSystem` with what the source states about where its coordinates sit, each part optional and never defaulted. The **world frame** is a `CoordinateFrame` (origin in canonical metres, right-handed orthonormal axes) in which the source's model coordinates are stated. **True north** is a unit plan direction. A **map conversion** (`MapConversion`) names the target reference system, the offset (easting, northing, height) in the map's unit, the unit plan direction of the source's X axis in the map, the scale, and the metres per map unit when that unit is known exactly (`None` otherwise, never assumed to be metres). A source that states nothing answers with all three `None`: not georeferenced is a fact, not a failure. Statements that are ambiguous, unsupported or unreadable are refused. The handle refuses a source it does not cover and an answer about another source; evidence must be exact, reviewable and from the source. Semantic adapters provide it without geometry; model comparison reads it (see [Model comparison](./comparison.md)).

Metric routing is exposed as `MetricRoutingServiceHandle`. The concrete handle wraps a backend-neutral trait object so it remains type-indexable in `ServiceRegistry`. Engine capabilities consume validated metric requests and bounded evidence; adapters keep native mesh and B-rep types behind the service. `AxiolidMetricRoutingService` implements it over host-declared surfaces, portals and connectors; see [Metric routing](./metric-routing.md).

Free-space area, fixed directional clearance, containment of a clearance footprint in scopes, and constrained placement search are exposed through `FreeSpaceServiceHandle`. The handle enforces exact request binding and preserves asymmetric proof requirements: one obstruction or placement witness may be sufficient, while clear and no-placement verdicts require complete evidence. Placement domains distinguish unrestricted, support-grounded, and anchor-frame offset searches. Supported found witnesses require exact whole-base support evidence bound to the requested object, found frame, and maximum gap. See [Free space and clearance](./free-space.md).

Walkable-region topology is exposed through `WalkabilityServiceHandle`. A trusted geometry backend supplies a complete exact snapshot; engine routing distinguishes definite-width, impossible, and uncertain-width paths without importing backend cells or geometry. Typed vertical connectors (lift, ramp, stair) join levels, and a rule can route while forbidding a kind. `AxiolidWalkabilityService` implements it. See [Walkability topology](./walkability.md).

Plan-projected areas are exposed through `PlanAreaServiceHandle`: an object's footprint and the overlap of two footprints, each a `PlanArea` interval whose evidence is exact exactly when the bounds coincide. Capabilities decide from the whole interval; one straddling a bound is not evaluated. The uncovered area of an object is its footprint outside the union of a cover's footprints, each grown by a stated length in every plan direction (the points within that distance of it); an empty cover leaves the whole footprint. The handle refuses a negative or non-finite growth and an object in its own cover, and hands the cover over sorted without repeats; a service that does not measure uncovered areas refuses by default, never answering with the footprint. `measure_outside_bands` is the area of an object's footprint outside a union of `PlanBand`s: a band between two objects along a plan direction is the convex hull of both footprints, cut to the positions along the direction that both reach, such as the strip between two parallel walls over the length they share. The handle refuses a band bounded by the measured object itself and hands the bands over sorted without repeats; a service that does not measure bands refuses by default.

Plan spans are exposed through `PlanSpanServiceHandle`: an object's longest plan diagonal (the largest distance between two points of its footprint), and the distance between two footprints' centroids or farthest points, each a `PlanLength` interval whose evidence is exact exactly when the bounds coincide. `measure_centre` locates the centroid itself as a `PlanCentre`: a plan point, the radius within which the true centroid lies (zero, and exact evidence, for an exact footprint), and a `CentrePlacement` saying whether it lies inside the footprint, outside it (an L-shaped room) or undecidably near its boundary; the handle refuses a centre naming another object, and a service that does not locate centres refuses by default. The closest distance between two footprints is the proximity service's `horizontal` projection and is not repeated here. An object without a footprint is refused, never zero, and so is one object measured against itself. `measure_rectangle` gives a footprint its own axes as a `PlanRectangle`: the rectangle of least area enclosing it, with a centre and the radius within which the true one lies, two unit axes (the first in `[0°, 90°)`, the second a quarter turn on) and how far each may be turned, and the half extents along them as intervals. Its `RectangleOrientation` says how well the axes are known: `Unique` when one orientation (up to quarter turns) has the least area, `Tied` when several do and another rectangle may have other sides, `Unproven` when the mesh approximates the shape, so the extents still bound the true footprint along these axes but the axes need not be its own. `width_and_length` answers only for a unique orientation; `long_axis` also needs one side surely longer, so a square has none; `long_axis_angle` bounds the acute angle between two long axes in degrees. Evidence is exact exactly when every bound is a point and the orientation is unique. The handle refuses a rectangle naming another object, and a service that does not orient footprints refuses by default, never answering with the axis-aligned box.

Facade areas are exposed through `FacadeAreaServiceHandle`: the area of an object's steep faces that face the outside, as a `FacadeArea` interval bound to the requested object, whose evidence is exact exactly when the bounds coincide. Which objects are spaces (the interior) is the adapter's host declaration; whether an object is external is the rule's selection, never the service's. An object without a body, or a measurement an unmeasured body could change, is refused, never zero.

Vertical extents are exposed through `VerticalExtentServiceHandle`: the elevations of an object's lowest and highest points as `ElevationInterval`s, bound to the requested object. The evidence is exact exactly when both elevations are points; a tessellated body's elevations are intervals. An object without a body or with an unmeasured one has no extent, never zero. The same handle measures a `DirectionalExtent`: the lowest and highest positions of the body projected onto any `MetricDirection`, such as an object frame's axis, bound to the requested object and direction; `length_metres` is their difference as an interval sure to hold the exact value. Its evidence is exact exactly when both positions are points. A service that measures elevations only refuses directions by default, never answering with the vertical extent. `VerticalExtent::height_metres` is the height as an interval, and `VerticalExtent::uncovered_height` the vertical difference between an object and a cover: bounds on the height of the object's extent outside every cover extent grown by a stated length below and above. The upper bound measures the object at its widest against each cover at its narrowest, the lower bound the reverse, so both hold the exact value wherever the elevations lie within their intervals.

Stair flights, ramps and headroom are exposed through `WalkingSurfaceServiceHandle`. A service reports positions, never derived lengths: for a straight flight, its base (the body's lowest point, where the first riser starts), its top, and each tread's elevation and the positions of its front edge (the nosing) and back edge along the horizontal direction the flight climbs; for a ramp, each sloped run's lowest and highest elevation and the positions of its ends along its own direction of steepest ascent. The contract computes risers, goings (nosing to nosing), tread depths, nosing projections, the flight's rise, and each run's rise, horizontal length and slope (rise over length) from those positions as intervals sure to hold the exact value, so no adapter can report a riser that disagrees with its treads. A flight ends in a riser when its top lies decidably above its last tread and on its last tread when no higher; anything between is refused. Evidence is exact exactly when every position is a point. Headroom answers a `HeadroomRequest` naming the subject and the obstacles, which are the rule's selection (sorted, deduplicated, never the subject): the least vertical clearance from the subject's walking surface (its upward-facing faces no steeper than 45°) to an obstacle's body directly above, `None` when nothing requested stands above it, and the obstacles whose clearance may be the least. An answer to another object or request is refused. Winders and turning flights, open risers, landing sizes, clear width, handrails and the slab connection are not part of this contract yet (#85); a service refuses a shape it cannot decide.

Triangle counts are exposed through `TriangleCountServiceHandle`: the number of triangles in the mesh the host produced for an object, bound to the requested object. The count is of the host's mesh, not of anything the source states, so another host or chord budget may count differently; the evidence is exact only when the mesh is the object's exact shape, and approximate for a tessellation of curved faces. A bodiless object counts none; an unmeasured one is refused.

Pairwise proximity is exposed through `ProximityServiceHandle`: object extents with their geometry fidelity, and per-pair separation, plan overlap, witnessed penetration, containment and the certified volume two closed bodies share. `measure_face_distance` measures the signed distance from a body to one class of another body's faces (top, side, bottom, any): positive inside the other body (a cover), negative outside (a protrusion); a service that does not measure it refuses by default. An object declared to occupy no material is refused with `ProximityError::NoBody`, a body that could not be measured with `Unavailable`: the two are different facts, and only the first may be read as "nothing there". Evidence exactness must match fidelity, so a tessellation of curved faces is always approximate. The engine's `candidate_pairs` broad phase consumes the extents. See [Clash, interference and distance](./clash.md).
