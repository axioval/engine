# Typed host services

The engine passes a `RuleContext` containing the immutable project view and a type-indexed `ServiceRegistry` to trusted capabilities. Applications register semantic or computational services explicitly; duplicate concrete service types are rejected instead of silently replacing an implementation.

Adapter crates are peers:

- OpenBIM implementations can provide semantic/property/relationship services.
- Axiolid implementations can provide geometry services for IFC, proprietary CAD, or any source able to lower geometry into Axiolid.
- ICDD implementations can provide project assembly and cross-document link services.
- Alternate geometry backends register the same source-neutral service interfaces.

Services reach a run through its `EvidenceSession`, bound to the source snapshots they were built from. An adapter's service records its own snapshots (`with_service`). A service the host builds itself, such as geometry meshed from the same file, records only a source identity, so the host states the snapshots it was built from (`with_host_service`). Both are checked the same way: at least one binding, no source twice, and every binding equal to the session's snapshot, so a service built from another revision is refused.

A session may hold several sources. An adapter builds one session per source, and `EvidenceSession::federate` combines sessions over disjoint sources into one: the project holds every object under its own source-qualified identity, every snapshot and declared discipline is kept, and each semantic service the members registered (property resolution, relationship selection, type hierarchy, classifications, integrity, object frames, coordinate systems) becomes one service bound to the snapshots of the members that had it. Each request goes to the member that owns its source (a property's object, a relationship's anchor, a classified or framed object, an integrity scan's source); a source no member covers is refused, never answered empty. A relationship request is answered over the part of its candidate universe in the anchor's member, since a member cannot relate objects it does not hold, and the answer is bound back to the whole request. Two members holding one source are refused (`DuplicateSource`), and so is a member that already holds a service federation cannot route by source (`UnfederableService`): register host services such as geometry on the federated session, bound to every snapshot they were built from. One member is returned unchanged.

A snapshot need not contribute an object. A model holding no objects (an IFC file with only presentation data, say) is an empty source: `EvidenceSession::try_new` accepts it, alone or beside other sources, and federation keeps it as a member like any other. Only an object whose source has no snapshot (`MissingSource`) and two snapshots of one source (`DuplicateSource`) are refused. So that an empty source is judged rather than silently absent, the runtime installs the run's sources per run as `SessionSources`, replacing any host-registered copy: every snapshot's source in `Runtime::run_session`, the sources the objects name in `Runtime::run` over a bare project. A capability forming one scope per source (`object-count`, `table-allocation` without anchors) starts from these, so "the model contains a building" fails on an empty model instead of passing because nothing was counted.

A source's discipline (`EvidenceSession::with_discipline`) is a host declaration, not part of the snapshot identity: services bound to a snapshot stay valid whatever discipline the source plays. A host may instead assign disciplines from source metadata with a `DisciplineMap` (`EvidenceSession::with_discipline_map`): ordered wildcard rules over one metadata field each, the first matching one assigning its discipline to a source that declares none. A declared discipline is never replaced; a source whose field a rule reads was never stated keeps none, since that rule might have matched (`UnmappedReason::Unread`). `SourceDisciplines::origin` tells a declared discipline from a mapped one, naming the rule and the value. The runtime installs the session's declarations per run as `SourceDisciplines`, replacing any host-registered copy, as it does concept bindings. Source metadata (`EvidenceSession::with_source_metadata`: file name, applications, schema, project) is kept the same way and installed per run as `SourceMetadataIndex`; a snapshot's schema fills the `schema` field unless stated. Each field is unread or read completely; statements add up field by field, and a field stated twice with other values is refused.

Rule packages cannot register services and cannot supply executable code. Missing required services must produce an explicit not-evaluated/backend-unavailable outcome, never a pass.

Property resolution is exposed through `PropertyResolutionServiceHandle`. A present response is a `ResolvedProperty` bound to the complete `PropertyRequest`, including the source-qualified object identity and property key; absence requires equivalent exact request-bound evidence. The handle rejects cross-object substitution, mismatched property keys, absent provenance, approximate values, non-finite numerics, and non-reviewable absence claims. Built-in property capabilities and property-based selectors require this service rather than treating a missing entry in an object map as proof of absence.

The same handle enumerates an object's properties (`enumerate`), for rules that name sets and properties by pattern. A `PropertyEnumerationRequest` states, for the set and for the property, a `NameMatch`: `Any`, `Exact` or `Pattern` (a `NamePattern`, a regular expression matching whole names; rules compile XML Schema patterns into it). The answer, a `PropertyEnumeration`, is every property of the object the request selects, sorted by set and name, each set and name once, each with exact evidence, together with exact evidence that nothing else is selected: an empty enumeration proves absence as `CompletePropertyAbsenceEvidence` does for one name, so the trait's default refuses (`Unavailable`) instead of answering empty. Enumeration covers the source's own sets and never the reserved ones (`axioval:attributes` and the like), which are resolved by name only; an exact reserved set is an invalid request. The handle rejects an answer to another request, a property the request does not select, a repeated one, and inexact or foreign evidence. Federation routes enumeration by the object's source like resolution.

Relationship-based comparison candidates are exposed through `RelationshipSelectionServiceHandle`. A request binds the checked object, the complete selector-derived candidate universe, and either a shared-group or directional traversal query. Successful responses must stay inside that universe, use canonical unique object IDs and evidence, and prove exact completeness. Source adapters interpret native containment, hosting, and relationship structures; the engine does not read `Object.relationships` as authoritative source semantics.

Relationships derived from geometry are exposed through `DerivedRelationshipServiceHandle`. It answers the same `RelationshipSelectionRequest`s for identities starting with `axioval:derived.`, returning a `CompleteRelationshipSelection` or a refusal. `EvidenceSession::with_derived_relationships` registers it and replaces the session's relationship handle with one that routes those identities to it and every other identity to the semantic service registered before, so every capability that takes a `relationship` or a `path` uses derived relationships unchanged. The identity names the derivation and fixes its tolerances as `;key=value` pairs; an unknown derivation, an unknown or repeated key, or a negative, non-finite or out-of-range value is an invalid request, never an empty answer. The handle refuses a selection whose evidence does not name its derivation.

| Identity | Edge | Parameters (default) |
|---|---|---|
| `axioval:derived.contained-in-space` | an element to every space whose body contains its reference point; when none does, to the single nearest space whose surface lies within `horizontal` metres in plan and `vertical` metres in elevation of it | `horizontal` (0), `vertical` (0) |
| `axioval:derived.adjacent-space` | a door, window or opening to the spaces a probe first enters on each side of it within `reach` metres; a side that enters none is outside | `reach` (1) |
| `axioval:derived.overlapping-group-space` | a space to every larger space covering at least `ratio` of its footprint whose vertical extent lies within `vertical` metres of its own | `ratio` (0.5), `vertical` (0) |
| `axioval:derived.spans-level` | a space to every level (storey) whose height band, from its elevation up to the next level's, the space's vertical extent reaches at least `overlap` metres into, or at least half the space's own height: its own storey, and both storeys of a two-storey atrium | `overlap` (1) |

`axioval:derived.same-level` (`LevelMatch`: `by=elevation` with `tolerance`, or `by=name`) is not routed to a geometry provider: it matches containers a capability has already reached, by what their sources state (`LevelMatch::same` over `LevelFacts`), so a path step naming it is refused as an unknown derivation. See [Levels across models](./capabilities.md#levels-across-models).

Edges run from a subject to a space (a level, for `spans-level`): `forward` from a component reaches its space, `backward` from a space reaches its components or doors, and `backward` from a storey the spaces spanning it. Tolerances live in the identity rather than in a request field so that the request contract stays the one every relationship capability already builds, and two rules asking with different tolerances ask visibly different questions. An undecided case refuses the whole answer: an unmeasured or bodiless space, an unmeasured subject in the universe, a reference point or probe start on a space boundary, two equally near spaces, or tessellated geometry close enough to change the answer.

The adjacency evidence records sides, and that record is a contract: after the canonical identity and a colon, a provider cites `{subject}->{space}:side={+|-}…` for every space a probe first entered and `{subject}:side={+|-}…:outside…` for a face that entered none, `+` being along the element's through-thickness normal. `adjacent_side` reads a locator back as an `AdjacentSide` for a given subject and space (or outside), so a capability can require the spaces of an internal door on opposite faces.

Object frames are exposed through `ObjectFrameServiceHandle`: for an object, its placement frame as a `MetricFrame` (origin in canonical metres, right-handed orthonormal right, forward and up axes) grounded on that object, and an `ObjectFront`. The handle refuses objects of a source the service does not cover and a frame naming another object; the frame's evidence must be exact, reviewable and from the object's source. The frame's axes are the source's placement axes: `forward` is the placement's second axis and says nothing about which side of the object is its front. A front is `Stated` only where the source states one and `NotStated` otherwise, never inferred from the axes, the shape or the object's type. An object whose source states no placement is `NotPlaced`, never placed at the origin. Semantic adapters provide this service, so capabilities can use it without geometry.

The same handle answers a door's leaves and a window's panels (`ObjectFrameServiceHandle::leaves`, a `DoorLeaves`; the types keep their door names): the operation type as the source names it, the overall width and the lining thickness where stated, and per `DoorLeaf` its closed position (an origin and the door's width direction `along`, `width` metres long), the direction it opens towards (`opening`), the door's up axis, its thickness where stated, its motion (`Swing`, `DoubleSwing`, `TiltAndTurn`, `Tilt`, `Slide` with a direction, `RollUp`, `Removable`, `Fixed`), and for a hinged leaf its `HingeSide` (seen from above looking along `opening`) and `SwingSector`. The three axes are orthonormal but may be left-handed (`is_mirrored`). A sector is the symbolic swing: a quarter disc about the hinge from the closed leaf (`closed`) to the leaf open at right angles (`open`), a half disc for a double-acting leaf; `plan_bounds` brackets its footprint between an inscribed and a circumscribed convex polygon. The trait method refuses by default (`DoorLeavesError::Unsupported`), and a source that does not state what the leaves need answers `NotStated`, never a default; an operation it cannot place exactly (folding, revolving, contradictory panels) is `Refused`. The handle refuses doors of an uncovered source and leaves of another door; the evidence must be exact, reviewable and from the door's source. A window's panel also states its height (`height_metres`, set through `DoorLeaf::with_height`) and, when it tilts on a top or bottom hinge, its tilt sector (`tilt`, through `with_tilt`): a `SwingSector` in the vertical plane through one end of the hinge, whose radius is the height, from the closed panel along `up` to the panel lying open towards `opening`; the panel sweeps it along its width. A tilt-and-turn panel has both a swing and a tilt and counts among `hinged`; a tilting leaf without its tilt is invalid. For a window the operation is its partitioning (`SINGLE_PANEL`) and `LeafPosition` adds `Bottom` and `Top`.

Source coordinate systems are exposed through `CoordinateSystemServiceHandle`: for a source, a `SourceCoordinateSystem` with what the source states about where its coordinates sit, each part optional and never defaulted. The **world frame** is a `CoordinateFrame` (origin in canonical metres, right-handed orthonormal axes) in which the source's model coordinates are stated. **True north** is a unit plan direction. A **map conversion** (`MapConversion`) names the target reference system, the offset (easting, northing, height) in the map's unit, the unit plan direction of the source's X axis in the map, the scale, and the metres per map unit when that unit is known exactly (`None` otherwise, never assumed to be metres). A source that states nothing answers with all three `None`: not georeferenced is a fact, not a failure. Statements that are ambiguous, unsupported or unreadable are refused. The handle refuses a source it does not cover and an answer about another source; evidence must be exact, reviewable and from the source. Semantic adapters provide it without geometry; model comparison reads it (see [Model comparison](./comparison.md)).

Metric routing is exposed as `MetricRoutingServiceHandle`. The concrete handle wraps a backend-neutral trait object so it remains type-indexable in `ServiceRegistry`. Engine capabilities consume validated metric requests and bounded evidence; adapters keep native mesh and B-rep types behind the service. `AxiolidMetricRoutingService` implements it over host-declared surfaces, portals and connectors; see [Metric routing](./metric-routing.md).

Free-space area, fixed directional clearance, containment of a clearance footprint in scopes, and constrained placement search are exposed through `FreeSpaceServiceHandle`. The handle enforces exact request binding and preserves asymmetric proof requirements: one obstruction or placement witness may be sufficient, while clear and no-placement verdicts require complete evidence. Placement domains distinguish unrestricted, support-grounded, and anchor-frame offset searches. Supported found witnesses require exact whole-base support evidence bound to the requested object, found frame, and maximum gap. See [Free space and clearance](./free-space.md).

Walkable-region topology is exposed through `WalkabilityServiceHandle`. A trusted geometry backend supplies a complete exact snapshot; engine routing distinguishes definite-width, impossible, and uncertain-width paths without importing backend cells or geometry. Typed vertical connectors (lift, ramp, stair) join levels, and a rule can route while forbidding a kind. `AxiolidWalkabilityService` implements it. See [Walkability topology](./walkability.md).

Plan-projected areas are exposed through `PlanAreaServiceHandle`: an object's footprint and the overlap of two footprints, each a `PlanArea` interval whose evidence is exact exactly when the bounds coincide. Capabilities decide from the whole interval; one straddling a bound is not evaluated. The uncovered area of an object is its footprint outside the union of a cover's footprints, each grown by a stated length in every plan direction (the points within that distance of it); an empty cover leaves the whole footprint. The handle refuses a negative or non-finite growth and an object in its own cover, and hands the cover over sorted without repeats; a service that does not measure uncovered areas refuses by default, never answering with the footprint. `measure_outside_bands` is the area of an object's footprint outside a union of `PlanBand`s: a band between two objects along a plan direction is the convex hull of both footprints, cut to the positions along the direction that both reach, such as the strip between two parallel walls over the length they share. The handle refuses a band bounded by the measured object itself and hands the bands over sorted without repeats; a service that does not measure bands refuses by default. The coverage of an object answers a `CoverageRequest`: its footprint, the sources whose effect areas cover it (each `Participant` certain or possible), one `EffectReach` for all of them (`Grown`, `Travel` or `Visible`) with a range, and the blockers travel and sight avoid. The answer (`CoverageEvidence`) gives the footprint, the covered part of it as a `PlanArea` interval (its lower bound from the certain sources' inner bounds, its upper from every source's outer bound) and, per source, whether its effect meets the footprint surely, possibly, not at all, or could not be measured. The request refuses a negative range and an object that is both subject, source or blocker; the handle refuses an answer about another subject or not listing the requested sources in order; a service that does not measure coverage refuses by default.

Lines of sight are exposed through `SightServiceHandle`. A `SightRequest` names an eye point in canonical metres, a target, the blockers (the rule's selection, sorted, never the target) and optionally a range. The answer (`SightEvidence`) bounds the distance from the eye to the target's nearest point and gives the outcome: `Visible` with a witness point on the target, `Hidden` with the occluders, which must be requested blockers, or `Undecided`; no outcome only for a target surely beyond the range. The handle refuses an answer about another target, naming an occluder the request did not send, or skipping a target that may lie within range.

Plan spans are exposed through `PlanSpanServiceHandle`: an object's longest plan diagonal (the largest distance between two points of its footprint), and the distance between two footprints' centroids or farthest points, each a `PlanLength` interval whose evidence is exact exactly when the bounds coincide. `measure_centre` locates the centroid itself as a `PlanCentre`: a plan point, the radius within which the true centroid lies (zero, and exact evidence, for an exact footprint), and a `CentrePlacement` saying whether it lies inside the footprint, outside it (an L-shaped room) or undecidably near its boundary; the handle refuses a centre naming another object, and a service that does not locate centres refuses by default. The closest distance between two footprints is the proximity service's `horizontal` projection and is not repeated here. An object without a footprint is refused, never zero, and so is one object measured against itself. `measure_rectangle` gives a footprint its own axes as a `PlanRectangle`: the rectangle of least area enclosing it, with a centre and the radius within which the true one lies, two unit axes (the first in `[0°, 90°)`, the second a quarter turn on) and how far each may be turned, and the half extents along them as intervals. Its `RectangleOrientation` says how well the axes are known: `Unique` when one orientation (up to quarter turns) has the least area, `Tied` when several do and another rectangle may have other sides, `Unproven` when the mesh approximates the shape, so the extents still bound the true footprint along these axes but the axes need not be its own. `width_and_length` answers only for a unique orientation; `long_axis` also needs one side surely longer, so a square has none; `long_axis_angle` bounds the acute angle between two long axes in degrees. Evidence is exact exactly when every bound is a point and the orientation is unique. The handle refuses a rectangle naming another object, and a service that does not orient footprints refuses by default, never answering with the axis-aligned box.

`measure_recesses` finds the recesses of an object's footprint as `PlanRecesses`: every pocket between the outer boundary and the convex hull, each a `PlanRecess` with its mouth (the hull edge closing it) and its width and depth as `PlanLength`s; the handle refuses recesses naming another object. `measure_section` intersects the footprints of several objects into a `PlanSection`: its area interval, exact exactly when a point, and for a section that is not empty the short and long sides of its least-area rectangle, the same rectangle `measure_rectangle` answers, stated only when its orientation is unique (a tied section is refused); the handle refuses an empty request and a section naming other objects. A service that does neither refuses both by default, never answering that there is no recess or no section.

Shelf lengths are exposed through `LinearQuantityServiceHandle`: the running metres of shelving a layout of the requested `ShelfGeometry` places in a space, as a `LinearInterval` holding the layout's length on the true geometry. The doors and openings whose clearances carry no shelving are the rule's selection, carried in the request (`LinearQuantityRequest::with_doors`), never the host's. The evidence may carry the space's clear height (`with_clear_height`), so a rule can tell a space too low for the shelving from one too small.

The same handle finds corridor ends (`measure_corridor_ends`, refusing by default). A `CorridorEndRequest` names a space and the subjects to measure (its windows, say; sorted, deduplicated, never the space). The answer, `CorridorEnds`, lists the ends of the paths through the space's footprint, each a `CorridorEnd` with a plan point inside the footprint, a clearance interval (distance to the nearest wall) sure to hold the true value, and an `EndWall`: `Decided` with the straight run of the footprint's boundary the path runs into and every requested subject against it as a `WallContact` (the plan `gap` between the subject's footprint and the wall segment, and the length of the segment it `facing`s, the overlap of its projection onto the wall's line with the segment, both `PlanLength` intervals), or `Undecided` with the reason. The paths come from an approximate skeleton, so `CorridorEnds` evidence is never exact: which ends exist and where the axis runs are not certified, and a service decides a wall only when the approximation cannot change it. The handle refuses an answer about another space or a decided wall not measured against exactly the requested subjects in order. Whether an opening in an end wall is allowed is a rule's judgement.


It also measures what lies beside an object's sides (`measure_side_distances`, refusing by default). A `SideDistanceRequest` names the object, the candidates (sorted, deduplicated, never the object), a reach and an inset. The sides are those of the object's least-area rectangle, as `RectangleSide`s (along or against each axis); a rectangle whose orientation is not unique has none, and the answer refuses it. A side's strip is the region beyond the rectangle's centre line square to the side, out to the reach, whose offset across the side lies within the rectangle's half extent across it, less the inset on both edges. `SideDistances` carries the rectangle and, per side, every candidate that may meet the strip with positive area, as a `SideDistance`: `Sure` or `Possible` presence, and the least distance from the centre line of its part in the strip as a `PlanLength` interval sure to hold the true value. A candidate not listed surely does not meet the strip. The rectangle's centre and axis errors, a tessellated candidate's chord deviation and the rounding of the clipping all widen the strip and the distances, so the evidence is never exact. The handle refuses an answer to another request. Which side is a component's back, or whether its axis lies far enough from a wall, is a rule's judgement.

Facade areas are exposed through `FacadeAreaServiceHandle`: the area of an object's steep faces that face the outside, as a `FacadeArea` interval bound to the requested object, whose evidence is exact exactly when the bounds coincide. Which objects are spaces (the interior) is the adapter's host declaration; whether an object is external is the rule's selection, never the service's. An object without a body, or a measurement an unmeasured body could change, is refused, never zero. `measure_face_area` answers, in the same `FacadeArea` form, the area of the object's largest plane face (all its faces in one plane, such as a wall's side less its openings); a service that does not measure it refuses by default.

Vertical extents are exposed through `VerticalExtentServiceHandle`: the elevations of an object's lowest and highest points as `ElevationInterval`s, bound to the requested object. The evidence is exact exactly when both elevations are points; a tessellated body's elevations are intervals. An object without a body or with an unmeasured one has no extent, never zero. The same handle measures a `DirectionalExtent`: the lowest and highest positions of the body projected onto any `MetricDirection`, such as an object frame's axis, bound to the requested object and direction; `length_metres` is their difference as an interval sure to hold the exact value. Its evidence is exact exactly when both positions are points. A service that measures elevations only refuses directions by default, never answering with the vertical extent. `VerticalExtent::height_metres` is the height as an interval, and `VerticalExtent::uncovered_height` the vertical difference between an object and a cover: bounds on the height of the object's extent outside every cover extent grown by a stated length below and above. The upper bound measures the object at its widest against each cover at its narrowest, the lower bound the reverse, so both hold the exact value wherever the elevations lie within their intervals.

Stair flights, ramps and headroom are exposed through `WalkingSurfaceServiceHandle`. A service reports positions, never derived lengths: for a flight, its base (the body's lowest point, where the first riser starts), its top, and each tread's elevation and the positions of its front edge (the nosing) and back edge along the flight's walking line; for a ramp, each sloped run's lowest and highest elevation and the positions of its ends along its own direction of steepest ascent. The contract computes risers, goings (nosing to nosing), tread depths, nosing projections, the flight's rise, and each run's rise, horizontal length and slope (rise over length) from those positions as intervals sure to hold the exact value, so no adapter can report a riser that disagrees with its treads. A flight ends in a riser when its top lies decidably above its last tread and on its last tread when no higher; anything between is refused. Evidence is exact exactly when every position is a point. Headroom answers a `HeadroomRequest` naming the subject and the obstacles, which are the rule's selection (sorted, deduplicated, never the subject): the least vertical clearance from the subject's walking surface (its upward-facing faces no steeper than 45°) to an obstacle's body directly above, `None` when nothing requested stands above it, and the obstacles whose clearance may be the least. A tread or run may also report the positions of its two sides along `across` its walking direction (a quarter turn anticlockwise; a turning flight's tread walks square to its nosing), stated only where it fills that rectangle; the contract derives each width and the flight's, its narrowest tread's, which a winder, filling none, leaves unmeasured. A `LandingRequest` names a subject, a `WalkingEnd` (a flight's bottom or top, a run's bottom or top) and the candidate objects, the rule's selection; the `LandingEvidence` answering it reports the direction leaving the end, the end's arrival line along it (the first riser, the last riser, the run's end) and the `Landing`: the candidate (or, for a ramp, the subject) whose level surface meets the end, with its far side and sides when it is a rectangle along that direction, `None` when nothing requested carries one. Depth and width are derived from those positions. A `ClearanceBelowRequest` names a subject and spaces; `ClearanceBelow` is the least height of the subject's underside above a requested space's floor (its downward-facing level faces), leaving out where the subject rests on it, `None` when it stands above none, never exact. Both methods refuse by default, so a service that does not measure them never answers that there is no landing. A `HandrailRequest` names a subject, a `WalkingStretch` (a flight, or a ramp's run), the rails (the rule's selection), how far outside the walking surface's sides and above its pitch line a rail may lie (`reach`, `above`) and the extension beyond each end over which a rail's rise is measured. `HandrailEvidence` answers it with the direction, the positions along it where the pitch line starts and ends, the walking surface's sides, and per rail running along the stretch a `RailMeasurement`: its positions along and across, the least and greatest height of its top above the pitch line, and how much its top rises and falls over the extension beyond each end where it reaches that far. The contract derives each rail's extension beyond both ends and the `RailSide` it runs along (the half of the width that holds it wholly, as seen climbing), the pieces of the handrail along each side in order (`side_rail`: each starting and ending decidably further along than the one before, otherwise refused with their names) and the gap in plan between two pieces (`gap`, the least distance between the rectangles they fill); the evidence is never exact, and `measure_handrails` refuses by default. A turning flight's landing is placed along its end tread's direction, square to that tread's nosing, as projections in plan rather than arc lengths; a service refuses an end on a winder. Its handrails answer in `StretchPart`s (`HandrailEvidence::try_in_parts`): the flight's straight runs of treads, each with its direction and sides, every `RailMeasurement` measured in one part (`in_part`), the pitch line starting along the first part and ending along the last. The contract derives a rail's side from its part's sides, its extension only beyond the end its part holds (`None` otherwise), orders a side's pieces part by part and measures gaps between rectangles in their own parts' frames. A `ClearWidthRequest` names a subject, a `WalkingStretch`, the obstacles (the rule's selection) and a band `(from, to)` above the pitch line; `ClearWidthEvidence` answers with the narrowest clear width along the stretch, the least over positions between its ends of the distance across between the innermost points the obstacles reach within the band from each side (the walking surface's own side where none reaches in), as an interval, and the obstacles bounding the narrowest place; `measure_clear_width` refuses by default, never answering with the walking surface's own width. An answer to another object or request is refused; a service refuses a shape it cannot decide.

A flight is requested with a `TreadFlightRequest`, which says where a turning flight's walking line runs (`WalkingLinePlacement`): midway across its treads (the centre line), or a stated distance from the side it turns towards; an answer to another request is refused. The answer's `WalkingLine` is `Straight` (a horizontal direction; positions are projections onto it, and every line along a straight flight gives the same goings, so the placement does not apply) or `Turning` (a plan polyline with a vertex on every tread; positions are arc lengths along it, before its first vertex and after its last along its end segments extended). A tread may also carry its nosing as a `PlanSegment` (ends known within a radius), and whether the riser below it is closed (`RiserClosure`: `Closed`, `Open` or `NotMeasured`); the flight may carry its final riser's. The contract derives each winder angle, the plan angle between consecutive nosings, as an interval covering every direction the nosings' ends allow, and none where a nosing is too short for its radius.

`AxiolidWalkingSurfaceService` measures a straight flight's or a run's clear width by clipping every obstacle triangle to the band (between the stretch's ends and sides, the heights above each segment of the pitch line) and evaluating the free width at the clipped polygons' vertices and the ends, where its least value lies; an obstacle reaching over the walking surface's middle, or one that may enclose the band without a face in it, refuses, and so does a turning flight. It measures a flight from the planes plane detection finds (`axiolid_inspect::detect_planes`, axiolid/kernel#131): treads are the level planes facing up, each certified within the level tolerance (a placement's rounding plus twice a tessellation's chord deviation), so treads and risers are separate planes. A tessellated flight is measured with every position widened by its chord deviation, never exactly. Treads whose centres follow one line make a straight flight; otherwise the flight turns, and its walking line is built from each tread's nosing and back edge: a tread with parallel edges is crossed along its nosing, a winder along the bisector of its edges (a tread with parallel edges states its sides where it fills a rectangle across its nosing, a winder none), and the inner side is the one its winders turn towards (winders turning both ways leave none, so a line from the inner side is refused). A riser between two treads is `Open` where the lower tread's back edge meets a face falling away, `Closed` where every part of it meets a face rising (how far is not measured); the first riser is `Closed` when faces in its nosing's vertical plane cover the strip below it down to the base, and otherwise `NotMeasured`, since a riser set back behind a nosing looks the same.

Space-boundary coverage is exposed through `BoundaryCoverageServiceHandle`. A `BoundaryCoverageRequest` names a space and a plane tolerance; the `BoundaryCoverage` answering it, bound to the request, reports as `SurfaceAreaInterval`s the space body's surface area, the part of it the space's declared boundaries cover, the part they leave uncovered and the part two or more of them cover, every declared boundary as a `MeasuredBoundary` (its source-qualified identity, the element on its other side when the source names one, and whether it lies `OnSurface`, with its area, or `OffSurface`, covering nothing), and each pair of boundaries covering a common part (`BoundaryOverlap`). The covered share is derived from the covered and surface areas, never accepted from a service. Which boundaries a space has is the source's, registered by the host; a boundary whose surface cannot be read leaves the space refused, never measured without it. Evidence is exact only when every interval is a point. The method refuses by default, and an answer to another request is refused.

Triangle counts are exposed through `TriangleCountServiceHandle`: the number of triangles in the mesh the host produced for an object, bound to the requested object. The count is of the host's mesh, not of anything the source states, so another host or chord budget may count differently; the evidence is exact only when the mesh is the object's exact shape, and approximate for a tessellation of curved faces. A bodiless object counts none; an unmeasured one is refused.

Pairwise proximity is exposed through `ProximityServiceHandle`: object extents with their geometry fidelity, and per-pair separation, plan overlap, witnessed penetration, containment and the certified volume two closed bodies share. `measure_face_distance` measures the signed distance from a body to one class of another body's faces (top, side, bottom, any): positive inside the other body (a cover), negative outside (a protrusion); a service that does not measure it refuses by default. `measure_body_volume` answers the certified volume one closed body encloses as a `BodyVolume` bound to the requested object, widened for tessellation; a service that does not measure it refuses with `Unavailable`. An object declared to occupy no material is refused with `ProximityError::NoBody`, a body that could not be measured with `Unavailable`: the two are different facts, and only the first may be read as "nothing there". Evidence exactness must match fidelity, so a tessellation of curved faces is always approximate. The engine's `candidate_pairs` broad phase consumes the extents.
